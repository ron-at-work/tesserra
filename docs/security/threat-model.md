# ATTEST MVP Threat Model

- **Status:** Draft — Milestone 1 documentation-only security input
- **Profile:** ATTEST MVP protocol profile, version 1 (project-defined)
- **Date:** 2026-09-01
- **Owner:** Security architecture / Milestone 1 review
- **Scope:** Agent identity, delegation, signed request, provenance, trust, replay, and status semantics. This document specifies threats and required controls; it does not claim that an implementation exists.

## 1. Purpose and method

This threat model records the security claims that the proposed ATTEST MVP can and cannot make. It uses STRIDE as an organizing method, supplemented by abuse sequences and a threat/control/vector matrix. A valid signature is evidence that the holder of a resolved private key signed prescribed bytes. It is **not**, by itself, evidence that the signer is trusted, honest, authorized, uncompromised, fresh, or that an asserted action happened.

“Current mitigation” means a mitigation already specified by the proposed Milestone 1 protocol/security documentation and therefore required of a conforming future implementation. It does **not** mean deployed product code. “Future mitigation” names work that must be completed in the listed owner phase or later. A vector identifier is a planned conformance/adversarial fixture identifier; fixture files are deliberately not created by this threat-model task.

### 1.1 Security objectives

| ID  | Objective                   | Meaning                                                                                                                           |
| --- | --------------------------- | --------------------------------------------------------------------------------------------------------------------------------- |
| O1  | Authenticity                | Accept signed evidence only when exact bytes verify under one authorized, resolved key.                                           |
| O2  | Authorization integrity     | Authorize an action only under locally configured trust, valid status, required bindings, and a non-expanding delegation path.    |
| O3  | Context binding             | Prevent use of evidence outside its intended trust domain, audience, task, action, resource, time, and replay context.            |
| O4  | Freshness and single use    | Detect or prevent replay according to the selected online or offline mode, without claiming offline global freshness.             |
| O5  | Evidence integrity          | Preserve digest-bound provenance and verification evidence without treating mutable names or URLs as authority.                   |
| O6  | Determinism                 | Make parsing, canonicalization, verification ordering, and result codes reproduce across conforming implementations.              |
| O7  | Confidentiality and privacy | Avoid exposing private keys and minimize stable identifiers, capability chains, provenance details, and status-query correlation. |
| O8  | Availability within limits  | Bound resource consumption and fail safely; availability itself is not guaranteed.                                                |
| O9  | Auditability                | Record the input, decision, and policy/status snapshot identities needed to reproduce a decision without recording secrets.       |

### 1.2 In scope

The model covers the project-defined canonical JSON proof profile: strict UTF-8 I-JSON and RFC 8785 canonicalization; an exact `proof` object; canonical unpadded base64url; Ed25519 verification; domain-separated signing inputs; reference resolution; trusted key/status resolution; local trust snapshots; parent-linked attenuating delegations; expected-context binding; online challenges; offline verification limitations; status/revocation/rotation; provenance; local SQLite persistence planned for later phases; and future MCP/SPIFFE/A2A adapter boundaries. It is a project-defined proof profile.

### 1.3 Out of scope, but not invisible

The following are not supplied or replaced by ATTEST: an identity provider, OAuth/OIDC authorization server, PKI, KMS/HSM, workload-attestation system, policy engine, secure execution environment, agent framework, message transport, artifact registry, transparency log, malware detection service, or distributed availability service. Their compromise is nevertheless modeled when it affects ATTEST evidence.

## 3. Actors and attacker capabilities

### 3.1 Legitimate actors and components

| Actor/component            | Intended role                                                                  | Trust assumption boundary                                                        |
| -------------------------- | ------------------------------------------------------------------------------ | -------------------------------------------------------------------------------- |
| Root/recovery authority    | pins trust roots, authorizes recovery and administrative rotation              | Can change trust only through independently protected, auditable authority.      |
| Issuer/attester            | signs identity, attestation, status, or provenance claims within authorization | A signature proves key possession, not truthfulness.                             |
| Delegator/delegate         | passes only a strict subset of authority to a named delegate key               | Neither is trusted to self-enforce attenuation.                                  |
| Provenance producer        | emits statement about inputs, action, runtime, and outputs                     | Producer may be buggy, malicious, or compromised.                                |
| Relying party/verifier     | supplies expected context and applies local policy                             | Must obtain expected context from a trusted request path, not an object.         |
| Policy/status distributor  | distributes signed snapshots                                                   | May be stale, unavailable, equivocal, or compromised.                            |
| Replay store               | atomically tracks the policy-defined nonce/`request_id` replay key             | May fail, race, be rolled back, or be unavailable.                               |
| Artifact/resource store    | provides referenced bytes and immutable digests                                | Mutable names/URLs are not trusted evidence.                                     |
| Administrator/operator     | configures local service, storage, logs, backups, and exposure                 | May make unsafe deployment choices or act maliciously.                           |
| Optional adapter/transport | carries ATTEST evidence over MCP, SPIFFE, A2A, HTTP, or another protocol       | It must preserve required evidence or explicitly negotiate unsupported behavior. |

### 3.2 Attacker model

An attacker may be an unauthenticated network peer; a malicious tenant, subject, delegate, or tool/server; a compromised issuer, verifier, provenance producer, store, status distributor, or adapter; an insider with filesystem/log/backup access; a supply-chain attacker; or a network/clock adversary. The attacker can:

- create arbitrary malformed and large inputs, reorder or duplicate JSON members, exploit Unicode/number edge cases, and replay captured valid objects;
- control objects, URLs, metadata, task/resource labels, and any context obtained from an untrusted caller or transport;
- possess a stolen delegate or issuer key until key status reaches the verifier;
- delay, replay, suppress, reorder, equivocate, or roll back status/policy data and manipulate reachable clocks or network responses;
- race concurrent verification calls and cause crashes or storage failures;
- read or alter local files, SQLite state, logs, or backups when local host/storage access is obtained;
- cause CPU, memory, disk, connection, and network-fetch pressure; and
- correlate stable identifiers, chains, provenance, and status lookups visible to them.

The attacker is not assumed able to break Ed25519 or SHA-256, cause a conforming Ed25519 verifier to accept a non-canonical or small-order/subgroup-invalid key/signature encoding, defeat a correctly configured TLS channel, or compromise an independently protected root/recovery key. Those assumptions require ongoing cryptographic and operational review.

## 4. Deployment modes and safe local defaults

### 4.1 Deployment modes

| Mode                 | Description                                                                                | Material security distinction                                                                                                  |
| -------------------- | ------------------------------------------------------------------------------------------ | ------------------------------------------------------------------------------------------------------------------------------ |
| Local single-user    | A verifier and future SQLite store run on one developer or operator workstation.           | OS account, disk encryption, local backup handling, and loopback exposure dominate operational risk.                           |
| Local service / LAN  | A service operates for a small administrative domain.                                      | Caller authentication, administrator separation, remote exposure, and trusted time/status distribution are required.           |
| Connected production | A verifier has authenticated access to pinned policy and signed status distribution.       | Bounded freshness and rollback detection are feasible but distributor availability/equivocation remain risks.                  |
| Disconnected/offline | Verification uses supplied, pinned snapshots and a policy-supplied evaluation time.        | Cannot establish globally current revocation or globally one-time replay prevention.                                           |
| Federated/adapted    | SPIFFE, OAuth/OIDC, MCP, A2A, KMS/HSM, or other systems are mapped at explicit boundaries. | External credentials/transports retain their own semantics; mapping must not collapse principal types or weaken ATTEST checks. |

### 4.2 Safe local defaults

A future implementation MUST use these defaults unless an administrator makes an explicit, auditable override:

1. Bind administrative and verification APIs to loopback only; remote listening requires explicit configuration, caller authentication, transport protection, and an exposure warning.
2. Start with no trusted roots, issuers, remote fetch URLs, or permissive wildcard audiences/tasks/resources. Production trust-on-first-use is prohibited.
3. Accept only the pinned protocol version, object kinds, literal `Ed25519` proof algorithm, canonical unpadded base64url encodings, exact 32-byte public-key and 64-byte signature lengths, valid Ed25519 public-key/subgroup semantics, deterministic key IDs, configured reference kinds, and configured digest/resource types. Reject any noncanonical encoding, unsupported algorithm, malformed proof, unresolved/ambiguous reference, invalid key binding, or unknown critical semantics.
4. Keep network acquisition outside deterministic verification. Do not fetch a key, status object, policy, provenance link, or trust metadata from a URL selected by an untrusted object.
5. Default authorization to fail closed for unavailable, unknown, stale, future-dated, conflicting, unverifiable, sequence-regressed, or rolled-back trust/key/revocation status. Authenticate a pinned trust snapshot containing roots, issuer/status authorities, status high-water marks, maximum chain depth, and replay policy; select `offline-inspection-only` only explicitly and display its bounded-freshness limitation.
6. Use short, policy-limited validity windows; require explicit expected audience, task, action, resource, and immutable resource/subject digests from trusted request context. `payload_digest` and `task_context_digest` are mandatory request fields. The verifier MUST receive the corresponding expected immutable digests in VerificationContext and exactly compare both; absence or mismatch fails closed as `INVALID_DIGEST_LINKAGE`. Omitted authority means no authority.
7. Require an audience-scoped random online nonce and atomic one-time consumption where online replay resistance is required. Never report success when the required replay commit fails.
8. Bound envelope/object size, JSON depth/member count/string length, delegation/provenance graph depth and count, validation work, replay-store retention, and outgoing connection count. Reject over-limit input before expensive operations.
9. Store only opaque private-key provider references in future SQLite state. Redact authorization headers, credentials, private keys, raw sensitive prompts, and unneeded provenance parameters from logs, events, exports, and backups.
10. Make local SQLite data owner-readable only; use authenticated encrypted backups where available; preserve durable monotonic sequence and replay-consumption state; detect backup/database rollback rather than silently accepting it.
11. Display and audit snapshot IDs/hashes, evaluation time, mode, decision code, and redacted object IDs. Do not log complete signed payloads by default.
12. Treat adapter evidence as absent/unsupported when a required ATTEST field or negotiation signal is stripped. Do not silently downgrade to an unbound identity claim.

## 5. Components, entry points, data flows, and trust boundaries

### 5.1 Entry points

| ID   | Entry point                                      | Untrusted inputs or control plane                                                           |
| ---- | ------------------------------------------------ | ------------------------------------------------------------------------------------------- |
| EP-1 | Signed artifact ingestion                        | raw canonicalizable JSON bytes, artifact fields, `proof`, references, and signature         |
| EP-2 | Verification API/SDK/CLI                         | expected audience/task/action/resource bindings, mode, evaluation time, identifiers         |
| EP-3 | Trust/status/policy import                       | signed snapshots, sequence/epoch, storage location, administrator approval                  |
| EP-4 | Replay store                                     | policy-scoped nonce/`request_id` reservation and atomic consume operation                   |
| EP-5 | Provenance graph import/query                    | statement links, digest maps, predicate type, graph traversal parameters                    |
| EP-6 | Future local SQLite database and backup/restore  | database files, journal/WAL files, backup artifacts, filesystem permissions                 |
| EP-7 | Future adapter ingress/egress                    | MCP/A2A metadata, OAuth/SPIFFE references, Agent Card/transport headers, discovery metadata |
| EP-8 | Operations/logging/export                        | diagnostic values, audit/event records, support bundles, database exports                   |
| EP-9 | Optional network acquisition before verification | configured distributor endpoint and transport response; never object-selected URLs          |

### 5.2 Data-flow diagram

```text
 [Root/recovery admin] -- signed/pinned policy --> [Trust snapshot store]
                                                     | TB-1
 [Status authority] -- signed status/revocation --> [Status snapshot store]
                                                     | TB-2
 [Issuer/delegator] -- signed artifacts --> [Adapter/transport] -- raw bytes --> [Verifier]
 [Provenance producer] -- digest-bound statements --/                         | TB-3
 [Relying party] -- trusted expected context ----------------------------------+
                                                                              |
                                                        [deterministic checks + replay CAS]
                                                                              | TB-4
                                        [replay store] <----------------------+
                                                                              |
                                             [redacted result/audit] --> [operator/export]
                                                                              | TB-5
                                                  [future SQLite + protected backups]
```

### 5.3 Trust boundaries

| Boundary                                    | Crossing                                          | Required treatment                                                                                                                              |
| ------------------------------------------- | ------------------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------- |
| TB-1: administrative policy boundary        | root/trust snapshot enters verifier configuration | Independently authorized root/recovery update; signature/integrity verification, pinned identity, monotonic version/rollback handling, audit.   |
| TB-2: status distribution boundary          | key/revocation snapshot enters verifier           | Signed authorized status, sequence/epoch monotonicity, freshness/next-update checks, conflict handling, no untrusted discovery.                 |
| TB-3: caller and evidence boundary          | object and expected context enter verifier        | Strict bytes-first parse; expected context authenticated/owned by relying party; never trust object assertions as expectations.                 |
| TB-4: replay-state boundary                 | success decision commits state                    | Atomic compare-and-set/unique insert coupled to success; durable result; no success on commit failure.                                          |
| TB-5: local persistence/operations boundary | database, logs, backups, exports leave process    | least privilege, redaction, encryption/authentication where available, tamper/rollback detection, access audit.                                 |
| TB-6: adapter boundary                      | external protocol metadata becomes ATTEST input   | Explicit profile/negotiation; preserve bindings; reject stripped, altered, oversized, or unsupported evidence.                                  |
| TB-7: network acquisition boundary          | configured remote endpoint provides snapshots     | allowlisted configured origin, SSRF defenses, response limits, authenticated transport, signed content; acquisition separate from verification. |

## 8. Abuse sequences

### AS-01: stolen delegate key

1. An attacker obtains a delegate private key from a host, backup, or external key provider.
2. The attacker signs a request or child grant that remains within the delegate’s currently valid authority.
3. The verifier resolves the key and signature successfully; signature validity alone does not expose theft.
4. Containment depends on short validity, strict bindings, status freshness, and key/grant revocation.
5. Once a fresh signed revocation/status snapshot reaches a fail-closed verifier, the request fails under CTRL-08.

**Security conclusion:** scope/expiry reduce blast radius; revocation is not retroactive global knowledge. This is residual risk R-01 and is tested by `V-REVOCATION` (`cases/revoked.json`) plus planned stolen-delegate/revocation runtime timelines.

### AS-02: compromised issuer produces correctly signed lies

1. An authorized issuer signs an attestation claiming a task ran safely or a provenance statement omitting a malicious input.
2. The statement is canonical, correctly signed, and may satisfy all bindings.
3. The verifier can establish only that an authorized key made the claim under its policy scope.
4. Predicate allowlists, issuer scope, independent evidence, and revocation can limit acceptance; they cannot make a dishonest signer honest.

**Security conclusion:** ATTEST authenticates claims under policy, not truth. This is residual risk R-02, with future independent witness/transparency/workload-evidence work.

### AS-03: stale offline status accepts revoked authority

1. A verifier intentionally operates offline with a previously valid pinned status snapshot.
2. A key is revoked after that snapshot but before offline verification.
3. The attacker uses a previously authorized key and in-window object.
4. The verifier can enforce snapshot expiry and its policy-supplied evaluation time but cannot learn the unseen revocation.

**Security conclusion:** offline verification must be visibly opt-in with bounded status age and never claim current global revocation. This is residual risks R-04/R-05.

### AS-04: two concurrent nonce uses

1. The attacker sends two copies of a valid nonce-bound request concurrently.
2. Both parse, verify, and satisfy policy before replay consumption.
3. A transactional unique insert/compare-and-set decides one winner.
4. The loser receives a replay result; if persistence fails, neither request receives success.

**Security conclusion:** atomic state is part of the security decision, not a best-effort audit action. The planned `V-REPLAY` concurrency extension must specify exactly one success.

### AS-05: malicious canonical artifact JSON

1. An attacker sends an artifact with duplicate `audiences`, a lone surrogate, a precision-edge number, and visually confusable task text.
2. A nonconforming parser might keep one duplicate, normalize text, or serialize a different number before applying the project-defined proof verification.
3. A conforming verifier rejects duplicate/invalid I-JSON before semantics, canonicalizes permitted values, requires canonical-byte equality, and compares typed fields exactly.

**Security conclusion:** application objects must not be deserialized through permissive “last wins” JSON APIs. The `V-PARSE` family (`malformed/duplicate-member.json` and `malformed/complete-artifact-noncanonical-trailing-bits.json`) is the blocking baseline; its planned extensions cover the remaining parser boundaries.

### AS-06: provenance graph substitution

1. A producer supplies a provenance graph for a desired output but swaps a predecessor statement or points to a mutable tag that later resolves differently.
2. A consumer sees a familiar name and accepts the apparent lineage.
3. A conforming verifier treats names/URLs as non-authoritative, checks exact subject/material digests, predicates, parent references, graph limits, and completeness flags.

**Security conclusion:** a correctly signed but incomplete graph must remain visibly incomplete; ATTEST cannot prove that a producer disclosed every real input. A planned provenance graph family addresses structural substitution; completeness truth remains a signer-trust limitation.

### AS-07: recovery after root compromise

1. A root signing key is suspected compromised; attacker may issue trusted-looking future status or recovery data.
2. Administrators invoke independently pinned recovery authority using a predefined recovery policy.
3. Verifiers select only the authorized recovery path, reject delegate-issued recovery, retain prior snapshots for historical decision reproduction, and apply compromise policy to affected history.
4. Operators distribute the new trust snapshot and maintain monotonic/rollback-protected state.

**Security conclusion:** recovery is an operational ceremony with high residual trust, not an automatic self-healing property. A planned root/recovery extension suite verifies only authorization mechanics; custody is assumption A-01.

### AS-08: malicious tool/server

1. A validly authorized agent invokes a tool with a digest-bound resource/action.
2. The tool changes external state unexpectedly, returns fabricated output, or exfiltrates supplied data.
3. ATTEST can record the authority chain and digest-bound claimed result; it does not sandbox the tool or prove the response was truthful.

**Security conclusion:** downstream tool trust, execution safety, and data handling require separate controls. This is residual risk R-13.

### 9.2 Non-guarantees

ATTEST **does not** guarantee or prove:

- signer honesty, the truth of a signed claim, safe code, benign model behavior, correct execution, complete provenance, or uncompromised runtime/hardware;
- that a private key was not copied before compromise became known, or that a compromised authorized root/recovery authority will act correctly;
- current global revocation, status freshness, or one-time use while disconnected from the necessary synchronized state;
- secure key custody, user authentication, OAuth authorization, PKI, workload attestation, transport confidentiality, tool sandboxing, artifact safety, or policy correctness supplied by another system;
- availability under network, storage, status-service, or denial-of-service failures; or
- unlinkability. Required stable identifiers, content digests, chains, status records, and audit evidence can be correlatable.

ATTEST **does** aim to authenticate specific signed claims under explicit configured trust policy and to reject malformed, untrusted, unbound, non-attenuating, stale-by-policy, or replayed evidence deterministically when the required local state is available.

## 12. Approval criteria for this threat model

The Milestone 1 approval reviewer must confirm all of the following before implementation is authorized:

- Every T-01 through T-33 has a current documented control, an explicit remaining risk, a future mitigation/owner, and a planned test/vector or named untestable assumption.
- Every Critical and High threat maps to a normative RFC anchor and at least one negative/adversarial vector, except explicitly untestable truth/custody assumptions A-01, A-02, and A-05.
- The final RFC uses the same field names, interval semantics, replay keys, status precedence, decision codes, limits, and safe defaults referenced here.
- Every fixture path in the manifest occurs in §11 under exactly the family or families declared by that fixture, including multi-family fixtures; every cited `V-*` identifier is a manifest-declared family.
- All residual risks R-01 through R-15 have a named acceptance owner and are either accepted, reduced, or rejected before the “Approved for implementation” sign-off.
- No adapter, offline mode, local SQLite feature, audit record, or future transparency mechanism is represented as implemented until its approved phase passes its security gate.
